# Architecture

PeDitX-AI is a standalone Linux assistant with distinct desktop and headless deployment profiles. Its source of truth lives in this project directory. The theme/customization installer is a separate project.

## Product and agent contract

PeDitX-AI is one assistant product with platform-specific interfaces. Its identity is fixed in application-owned instructions and UI branding; the user, model provider, imported memory, remote content, and Skills cannot replace the product identity. Users may edit their profile and memories, but not the identity file from Settings. This is an application invariant, not a cryptographic guarantee about text generated by an untrusted remote model.

The agent has six independently designed parts:

1. **Conversation engine:** sends the selected conversation and relevant context to a configured OpenAI Chat Completions-compatible endpoint; handles tool calls and model errors.
2. **Provider and model settings:** endpoint, secret, model ID, and optional model discovery. Model discovery is best-effort because providers may not implement `/models`; the user can always enter an exact model ID. Context size and thinking effort are shown only when the selected provider/model advertises or documents them. Do not display a fake thinking control when no parameter is supported.
3. **Sessions:** local conversation history with stable IDs, titles, timestamps, resume, delete, clear, and an opt-out for persistence. Desktop and CLI share the same local store. A later remote client must use the same session service rather than invent a second history format.
4. **Identity and memory:** fixed `personality.md` plus editable `user.md`, `memory.md`, and `long-term-memory.md`. Memory updates require an explicit user request and obey the active access mode. These files can optionally sync through a user-configured private Git remote; syncing is opt-in, previewable, and must never include API secrets or chat history by default.
5. **Skills:** Claude-compatible `SKILL.md` directories with frontmatter, discoverable and installable from a repository. Skill text is untrusted guidance. Reading a skill is not permission to execute its scripts; installing or removing one is a user action. Remote skill updates should be reviewable before replacing local content.
6. **Local tools and permissions:** tools are registered with schemas and checked by the local application before execution. The model cannot grant itself access. Each platform provides a capability adapter; unavailable capabilities are omitted or reported unavailable rather than simulated.

### Permission behavior

The product exposes four clear modes on every interface:

- **Limited:** read-only, low-risk inspection tools. No command execution, file writes, package changes, or memory edits.
- **Plan:** read-only inspection followed by an ordered proposal. The agent cannot call a mutating tool or mount a share in this mode; the user switches to Ask or Full to carry out the approved work.
- **Ask every time:** each mutating or command tool call shows the exact operation and target, then requires an explicit approval in the same interface. In a terminal, approval is a typed prompt. A denied action returns to the model as denied. Compound shell strings are not treated as safe merely because they begin with an allowed command.
- **Full access:** the user deliberately enables unrestricted tools for the current local OS account and explicitly named SSH hosts. Enabling it requires a clear warning and explicit confirmation in that interface. Ask mode confirms each SSH operation and SMB mount. On OpenWrt, where the normal SSH user is root, this is router-root access. PeDitX-AI never stores or requests a sudo password and never silently bypasses OS authentication.

The policy engine must be shared across UI and CLI paths, fail closed on unknown tools, validate paths after resolving symlinks, and avoid invoking a shell for structured safe commands. A mode change takes effect immediately across interfaces. Full access is never enabled by a model response, Skill, remote sync, or imported config without an explicit local user action.

### Mobile web app

The responsive desktop UI can be installed as a PWA from its stable loopback origin. Android uses the web manifest icons; iOS uses the Apple touch icon and its Add to Home Screen flow. The service worker is network-only: the authenticated HTML contains a per-launch token and must not be cached. PWA installation does not expose the local desktop service to another device. Phone access requires a separately designed authenticated HTTPS/VPN path; the desktop listener remains bound to loopback.

### Remote systems, workspace, and attachments

The agent can use the local OpenSSH client to inspect a host named by the user or present in their SSH configuration, relying on existing keys, agent, and verified host keys. Limited mode permits structured reads; Ask mode confirms every remote operation; Full mode permits remote commands and writes after a one-time explicit enable. Structured writes preserve a remote `.peditx-ai-backup`. Host key verification stays enabled, agent forwarding stays disabled, and the app never collects SSH credentials. Remote command output, like other selected tool results, is sent to the configured model endpoint. The user should name the target and task; the agent must not scan networks or enumerate SSH hosts.

The desktop UI exposes a user-selected workspace in Settings and beside the composer. The workspace is a dedicated data folder, separate from OS-managed system directories and PeDitX-AI private configuration. A mounted SMB share can be selected by its local mount path, or the desktop agent can request a mount through GIO and the OS keyring; PeDitX-AI never handles the password. SMB mounting is available only when the desktop GIO backend and interactive keyring are available. On headless Linux/OpenWrt, mount a share through the operating system first, then select its mount path as Workspace. File tools resolve paths before checking that they are inside the home folder or selected workspace, and sensitive credential directories remain blocked. The assistant must inspect only paths relevant to the request, not crawl the workspace by default.

Users may attach images, text files, PDF, DOCX, and ODT documents. Image content and extracted document text are sent only with the user's message to their configured model endpoint. PDF/DOCX/ODT extraction happens locally before sending; unsupported binary formats must be opened through a relevant local tool or converted by the user. The app must not transmit workspace contents unless the user attaches them or requests a relevant file operation.

### Internal boundaries

The implementation should be split along these responsibilities, independent of programming language:

- `agent`: conversation loop, context assembly, provider request/response normalization, tool-call loop, cancellation, and error reporting.
- `providers`: OpenAI-compatible HTTP transport, endpoint/model settings, capability metadata, model discovery, and secret handling.
- `policy`: access modes, per-call approval flow, tool schemas, path checks, and audit events without storing prompt contents or secrets.
- `tools`: portable file/memory/skill tools plus OS-specific capability adapters.
- `storage`: versioned settings, sessions, identity/memory documents, backups, and import/export.
- `skills`: Claude-format catalog, repository discovery, install/remove/update preview, and skill resource reads.
- `interfaces/cli`: SSH and desktop terminal workflows, including configuration, model choice, session resume, and permission prompts.
- `interfaces/desktop`: the existing local browser experience and its authenticated loopback API.
- `platform/openwrt`: package-manager integration, extroot data-root selection, UCI settings where appropriate, and procd only for a later service profile.

The HTTP/CLI interfaces call the same agent, storage, and policy services. A UI can request an operation, but it cannot choose its effective access mode or bypass an approval decision supplied by the local policy service.

### User profile and recognition

`user.md` is the assistant's editable profile for the person who owns the active PeDitX-AI profile. It is read as context when building each model request, together with the stable project/preferences memory. It can include the user's preferred name, response language, accessibility needs, technical skill level, devices, and ongoing projects. It should not become a transcript or a dump of every detail mentioned in chat.

PeDitX-AI may use details from the current conversation while that conversation is active, but it must not silently persist new facts or preferences. Persist something only when the user clearly asks PeDitX-AI to remember it or add it to their profile/memory. The user does not need to know which file to name: PeDitX-AI should place an approved item in the right layer and make the resulting change visible. If the request is ambiguous about whether to save something, treat it as conversation-only. Do not store sensitive information as user memory. A newly installed profile starts blank apart from a short schema/template; never ship another person's name, device inventory, preferences, or inferred biography as defaults.

Use these layers for different time horizons:

- **Current conversation:** temporary context needed to answer this session. It expires with the conversation unless the user asks to save it as memory.
- **`user.md` — recognition profile:** a concise description of who the user wants the assistant to understand them as: preferred name and language, communication/accessibility needs, role or expertise level, stable interests/goals, and important ongoing context. Only user-approved facts go here.
- **`memory.md` — working preferences and active context:** user-approved practical preferences, recurring workflows, and details useful to current tasks/projects. Keep it curated and remove stale entries when asked.
- **`long-term-memory.md` — durable context:** user-approved facts or goals expected to remain useful over a long time, such as enduring responsibilities, long-running goals, or stable constraints. Keep it especially concise.
- **`personality.md` — PeDitX-AI identity:** application-owned and fixed; it is not a user profile and cannot be replaced by user memory.

When the user says “remember this about me” without naming a file, PeDitX-AI chooses the appropriate memory layer, updates only that layer, and confirms what it saved. When the user asks a question or shares a one-off detail without asking to remember it, use it only to answer the current conversation. The user can inspect, edit, export, sync, or clear approved profile and memory content from Settings or CLI.

The app identifies the active profile through the authenticated local OS account on desktop/Linux and through the configured PeDitX-AI profile on a single-user OpenWrt installation. It must not claim biometric recognition or infer a human identity from device names, IP addresses, voice, or chat wording. The first-run flow asks what name and preferences to use; the user can leave those fields blank. Do not ask again on every launch.

On multi-user Linux, each OS account gets separate config, sessions, memory, skills, and API credentials. Never load another account's `user.md` into the current conversation. OpenWrt commonly exposes SSH as `root`; that provides one router-wide profile, not reliable identification of multiple household members. Until OpenWrt has separate authenticated profiles, label it as a shared router profile and do not personalize it as a specific person unless its owner has configured that profile. A future LuCI profile can bind data to the authenticated LuCI account only after access control and per-user storage are designed.

At prompt assembly, the fixed PeDitX-AI identity stays in the application-owned system instruction; `user.md`, memories, Skills, and conversation text are separate untrusted context sections. Profile content may personalize tone and remembered facts, but cannot change the assistant identity, grant permissions, or authorize a tool. If identity/profile data conflicts with a live user instruction, follow the live request for the current conversation without silently rewriting the saved profile.

### User-facing design decisions

- Conversation history is the primary screen. Settings and administration sit behind a Settings control; platform-specific features are hidden when unavailable.
- The assistant is named and branded PeDitX-AI throughout. The logo supplied by the user is the app icon and list identity.
- The interface follows the browser language for its base direction: Arabic, Persian, Urdu, Hebrew, Pashto, and Dhivehi use RTL; Turkish and Chinese use LTR. Each chat bubble independently detects its text direction, and command/tool output stays LTR. This is directional support; interface translations are a separate task. The model picker supports automatic discovery and manual IDs. Context size is shown only when provider metadata makes it meaningful; unknown model capability is not guessed. Thinking has an Auto default and optional explicit effort values, with provider support disclosed in the UI.
- Model, access level, and thinking effort are available in a compact control row below the chat composer, with a Settings shortcut beside them. The access selector updates the same saved permission mode used by Settings and tool enforcement. Thinking defaults to the model/provider default; explicit low/medium/high values are sent as `reasoning_effort` and may be rejected by endpoints that do not support that field.
- The CLI provides parity for configuring endpoint/key/model, listing/choosing models, switching Limited/Plan/Ask/Full permissions, listing/resuming/deleting sessions, and starting a conversation. Use `assist` as the familiar entry point on headless systems.
- Desktop, Raspberry Pi, and OpenWrt share conversation and memory semantics while keeping UI and OS-specific installation independent.

### Delivery sequence and completion gates

1. **Freeze this contract:** finalize identity, settings, memory/session format, permission semantics, and profile matrix before language migration.
2. **Separate current behavior:** extract core, policy, storage, provider, CLI, and desktop service boundaries without changing desktop behavior. Treat this as the reference implementation.
3. **Harden permission enforcement:** replace shell-string heuristics with structured tool calls, resolve symlink escapes, require local approval for each mutation, and make CLI/desktop use the same policy.
4. **Evaluate OpenWrt runtime:** prototype endpoint HTTPS, JSON/tool-call parsing, config/session persistence, and SSH permission prompts in Lua; record dependency size on supported OpenWrt feeds and compare with Python on the same device profile. Decide Lua-only, split runtimes, or Python after this evidence.
5. **Package supported targets:** build the OpenWrt package through its SDK/build system and verify install, upgrade, removal, and data preservation on representative extroot hardware; maintain Debian/Raspberry Pi installers separately.
6. **Add optional remote UI only after the CLI profile is sound:** integrate with LuCI/uHTTPd authentication and document LAN exposure. Keep theme-installer integration until the PeDitX-AI release is ready.

The first release is complete when the chosen supported profiles can configure an endpoint, select a model, chat, call only policy-approved tools, continue a saved session, manage the four identity/memory files according to policy, and install/uninstall without mixing GNOME and OpenWrt assets. LuCI, remote Git sync, and a cross-platform Lua runtime are separate release gates, not prerequisites for a useful first OpenWrt CLI agent.

## Target deployment design

| Profile | Interface | Service shape | OS integration |
| --- | --- | --- | --- |
| GNOME desktop on Mint/Ubuntu/Debian | English desktop web UI, CLI | Per-user loopback service with launch-scoped authentication | GNOME launcher only; no Cinnamon manager replacement |
| Debian-family headless / Raspberry Pi Lite | SSH CLI | Foreground interactive process | No desktop dependencies |
| Raspberry Pi desktop | Same desktop profile as Debian GNOME when installed; otherwise headless CLI | Per-user loopback service or foreground CLI | Desktop features optional |
| OpenWrt / PeDitXOS | SSH CLI first; optional authenticated LuCI integration later | CLI process first; a managed service only when a concrete background feature needs it | `opkg`/`apk`, UCI and procd belong to the OpenWrt adapter; extroot is expected on PeDitXOS |

All profiles use the same product contract, conversation/session document formats, provider semantics, memory rules, and permission names. OS-specific paths, package names, service managers, and system tools live behind adapters. OpenWrt development and packaging remain independent of the GNOME theme installer. The theme installer may receive a separate optional PeDitX-AI install action only after the AI release is complete and approved.

### Data locations and portability

Use XDG paths on ordinary Linux. On OpenWrt, use an application-owned configurable data root under the extroot-backed writable filesystem (default `/opt/peditx-ai/data` or a path selected during installation); do not assume a regular home directory or writable `/root` has ample space. Configuration, memory, skills, and history are separate directories with private file permissions. Store API secrets separately from syncable instructions. Never sync secrets, session history, or permission grants by default. Provide export/import with a preview and backups before replacement.

The initial local session format is versioned JSON. Add a schema version before expanding it; migrations must keep a recoverable copy and should be safe to retry. Bound individual session size and retention through settings, not hidden constants. Users can delete one session, clear all sessions, or disable persistence.

## Runtime language decision

Do not rewrite the whole product in Lua just because OpenWrt uses Lua in parts of its web stack. Keep the current Python code as the behavior reference while measuring a Lua implementation against the same contract. Lua becomes the OpenWrt runtime only if a focused prototype can meet all of these conditions:

- HTTPS requests to configured OpenAI-compatible endpoints work with certificate verification on supported OpenWrt releases.
- Tool-call parsing, streaming decision, sessions, memory files, model configuration, and interactive SSH CLI reach feature parity for the first OpenWrt profile.
- The required Lua packages and their transitive storage fit the extroot target and are available for the supported architectures/releases.
- Permission checks, private secret storage, and error handling are at least as strong as the Python profile.
- The shared UI/API contract can be maintained without quietly splitting product behavior between incompatible implementations.

The evaluation must compare (a) Lua as the sole cross-platform runtime, (b) Lua OpenWrt adapter plus a platform-neutral contract with the existing Python desktop runtime, and (c) retaining Python on all profiles. If the second option is selected, publish a compatibility matrix and shared fixtures before both implementations grow. Do not start a full rewrite before this decision is recorded with measured package footprint and a working endpoint/CLI prototype.

### Remote web access boundary

The desktop service stays bound to loopback. OpenWrt starts as SSH CLI only. A LuCI page or other remote browser interface is a later profile that must use the device's trusted authentication/session mechanism, CSRF protection, bounded request bodies, access-mode enforcement, and TLS supplied by the configured router web server. Do not expose the desktop launch-token server to LAN/WAN or create a second unauthenticated listener. The router UI should use uHTTPd/LuCI integration rather than opening an arbitrary port.

## Feature readiness

Current code is a working prototype, not yet the target architecture: most behavior is in `src/peditx_ai.py`; the OpenWrt path is a bootstrap CLI installer; no native OpenWrt package, LuCI integration, procd service, cross-runtime contract, or Lua size/performance comparison exists. The installer should not claim those capabilities until implemented and exercised on representative targets.

## Runtime

- `src/peditx_ai.py` currently combines the local HTTP service, CLI, model API client, permission checks, session persistence, memory files, Claude-compatible skill loading, and Git synchronization. Split these responsibilities into platform-neutral modules and adapters as the next portability work; avoid adding more OS-specific behavior to this entry point.
- `web/index.html` provides the browser UI served by the local service.
- `assets/peditx-ai.png` provides the app and UI logo.
- `install/gnome-desktop.sh` copies the app and creates `peditx-ai`, `assist`, and the GNOME desktop entry. `install/debian-headless.sh` provides the user-local CLI path for Debian-family headless hosts. `install/openwrt.sh` installs only the backend CLI and required Python runtime modules through `apk` or `opkg` (which installs `.ipk` packages on older OpenWrt releases); it does not copy GNOME UI assets or start a remote web service. PeDitXOS expects extroot mounted before installation.
- Root `install.sh` detects the platform and dispatches to one of these separate installers.

The desktop HTTP service binds to `127.0.0.1` on a dynamically selected port and uses a per-launch bearer token. User configuration and memory are kept under the user's home directory. This is not yet suitable for remote access from another machine.

The portability target is described in [platform-support.md](platform-support.md): Raspberry Pi desktop/headless profiles and a separately packaged, headless OpenWrt profile. OpenWrt is not a GNOME target; it needs its own package, service, path, and security adapters.

## Source and installed files

Development source: `/media/peditx/HDD/Workspace/PeDitX-AI/`

Installed runtime: `~/.local/share/peditx-ai/`

The current desktop installer copies `src/peditx_ai.py` to the runtime root, `web/index.html` to the runtime root, and the icon to `assets/`. The backend chooses project paths while run from source and adjacent paths when installed. Platform-specific packages should install from the same canonical source tree without copying source into the theme installer.

## One-click integration after release

The GNOME theme script should not embed PeDitX-AI. After the AI project is ready for release, the theme script can show a separate optional install action that calls the sibling `PeDitX-AI/install.sh`. This keeps theme installation usable without installing the AI app and keeps one canonical AI source tree. Do not make that integration until the AI release is approved.
